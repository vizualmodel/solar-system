A browser application that calculates where celestial bodies are, then lets you explore that shared universe through independent 3D views.

The central idea is simple: share time and physics; give each view its own camera and presentation.

02 /

How an action travels through the app

The interface and renderers observe the same Svelte state. These walkthroughs show the main paths without implying a single synchronous ordering of every browser callback.

From startup to a rendered universe

  1. main.ts mounts App.svelte. The store attempts to validate and restore browser local storage; a restored session is paused. Otherwise it selects defaults, optionally using a URL preset.
  2. App starts the clock and fetches /data/ephemeris.json. While loading, the interface shows a loading message; a failed request produces an error screen.
  3. A derived calculation combines positions(data, time) with withSatellitePositions(...). These are physical coordinates shared by all views.
  4. ViewTree recursively mounts one Viewport per layout leaf. Each creates its own SolarRenderer, loads textures and starts a drawing loop.

One simulation clock, several drawing loops

  1. Play/date/speed controls generally call command(). It clones state, applies the command and validates before updating the store.
  2. startClock() schedules a browser animation callback. When playing, it adds elapsed real time × speed × one day to the simulation timestamp. Speed is expressed in simulation days per real second.
  3. Time is clamped to the selected start/end range and playback stops at a boundary. Each clock increment caps elapsed real time at 0.25 seconds to limit jumps after stalls.
  4. Svelte propagates the new time and derived physical positions. Each Viewport also has its own animation loop; rendering and camera damping continue while simulation playback is paused.

Duplicate the perspective, keep the universe shared

  1. store.split(id, direction) rejects a seventh view. Otherwise it clones the selected view configuration and assigns a new UUID.
  2. The new configuration joins views[]; the selected layout leaf becomes a row or column split containing the old and new IDs. The new view becomes active.
  3. The keyed Svelte tree mounts another Viewport and renderer. It receives the same ephemeris data, simulation time and physical positions.
  4. You can now change its camera, visibility or magnification independently. Closing a view removes its leaf and promotes its sibling; the last view cannot be closed.

Find the next local distance minimum

  1. The chart samples physical separation 100 times across the selected interval. Its sampled minimum is a coarse overview, separate from the event search.
  2. For two different planets, nextClosestApproach() scans distance slopes in six-hour steps, looking for a change from decreasing to increasing separation.
  3. The bracket is refined to about one second numerically. A one-minute skip avoids selecting the current event on repeated requests.
  4. A successful search changes the shared time and pauses playback while preserving views and cameras. No future minimum before TO produces a message and leaves state unchanged. Precision here is precision within the approximate model.

A validated request reaches the owning browser

  1. In companion mode, the panel submits a conversation turn to the local service and its Codex runtime. The agent invokes a structured MCP tool such as timeline.
  2. The service sends the request to its claimed browser with a correlation ID and expiry time. The browser adapter rejects expired requests and strictly parses the payload.
  3. applyControl() computes a proposed state. The adapter validates the operation before committing the simulation and any workspace UI changes.
  4. The client waits for Svelte updates and view readiness, then returns an acknowledgement. Commands are not queued for replay after a disconnect; read fresh state after a timeout.
The UI has several state-update paths. command() is a validated seam, but settings also use updateView() and some UI controls update stores directly. It would be inaccurate to say every human action passes through one central validator. The companion path explicitly parses, reduces and validates before commit.

Multiple views, one shared world

The layout is a recursive binary tree. Its leaves identify configurations in views[]; each leaf becomes a mounted viewport. The tree defines arrangement, not separate simulations.

The same tree becomes this screen
VIEW ASolar system

Independent camera and display settings

VIEW BEarth & Moon
VIEW CSurface telescope

Example arrangement only. The actual view names and camera choices are configurable.

Shared across every view

  • Simulation timestamp, playback and date range
  • Bundled ephemeris data and derived physical positions
  • The body catalogue and timestamp-based rotation model
  • One decoded CPU star-map texture cache

Owned by each view

  • Three.js scene, camera, WebGL context and drawing loop
  • Focus, tracking, camera position and target
  • Body visibility, labels, orbits and sky switches
  • Body size, moon spread and individual satellite magnification
  • Surface/alignment camera settings and Moon-shadow layers

Resource lifecycle: mounting creates a renderer and resize observer. Closing a view cancels its animation loop and disposes controls, geometry, materials, textures and the WebGL context. The decoded star map is shared, but each WebGL renderer still needs its own GPU texture copy.

Companion application

Static hosting does not supply the local Codex runtime. Scenario Setup and agent source changes require the connected local companion.

Boundaries that explain the design

These limits distinguish what the implementation does from what a larger or scientifically validated system would require.

An approximate astronomical model

The supported interval is 1 January 2025–1 January 2031 UTC. Blended Kepler states are not an N-body integration or exact Horizons reproduction.

UTC→TT assumes a fixed 69.184-second offset. Light-time effects, the periodic TT→TDB correction and future leap-second changes are omitted. Rotation excludes periodic libration/nutation; satellite frame conversion is approximate.

Tests of coverage, continuity and invariants do not establish reference positional accuracy. Moon shadows and eclipse cameras exist in the source, but their astronomical accuracy is not independently verified.

Graphics have a per-view cost

Each view is a complete WebGL renderer. The 8K star map shares one CPU decode, but its half-float GPU copy is roughly 256 MiB per renderer, before other assets.

Six views can therefore be expensive. The star map loads asynchronously; constellation imagery is resampled to 4K to bound its per-view memory. WebGL 2 is needed for the 3D application.

High playback speeds can alias rotation and short-period moon motion. Procedural spacecraft attitude is illustrative rather than telemetry.

Source versus older documentation: simulation-state.ts now owns the state model; scenario.ts is a compatibility wrapper. The source includes Moon shadows and special Earth cameras despite older “not modeled” text. Dedicated ±1-day UI buttons described in AGENTS.md were not found in the inspected Timeline component; the companion timeline reducer does support stepSeconds. This guide follows the implementation.
